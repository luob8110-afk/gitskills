# 冰山模型证据与判定规则

本文件是 `iceberg-evaluator` 的业务判定参考，适用于：

- `schema_version`: `2.2.0`
- `rules_version`: `p0.2-2026.08`

执行时以当前代码中的确定性校验为最终约束。模型负责从材料中提取候选证据、形成受约束的分析草稿；代码负责证据核验、置信度降级、阶段判定、推荐语生成及输出安全控制。

## 1. 输入、隐私与适用边界

1. 每次只评估一名候选人，输入为候选人简历、结构化面试问答和成功画像。
2. 简历只接受 UTF-8 文本，面试和成功画像只接受 UTF-8 JSON。
3. 面试材料必须包含非空 `candidate_name`、非空 `position` 以及 `interview_qa` 数组。
4. `interview_qa` 中每项的 `question_id`、`question`、`answer` 必须为字符串；只要问题或答案非空，就必须提供非空且唯一的 `question_id`。
5. 成功画像必须包含四个维度：`motivation`、`trait`、`self_concept`、`values`。权重必须为非负有限数，且总和大于 0。
6. 输入中出现年龄、性别、民族、婚育、孕育、健康、宗教、家庭背景等敏感字段时拒绝处理，不将其用于评价。
7. 调用模型前删除姓名和联系方式。报告优先使用输入中的候选人编号；没有编号时生成匿名标识。
8. 输出仅用于招聘证据整理和人工复核，不得自动作出录用、淘汰或其他雇佣决定。

## 2. 成功画像状态与治理要求

成功画像状态只能是：

- `draft`：试运行画像，只能进行探索性对照。
- `confirmed`：已确认画像，可进行受限的确定性对照。

画像还必须提供适用范围、成功定义、成功样本依据、水面上指标、维度定义、行为锚点、目标分和权重。

`confirmed` 状态必须额外提供完整治理信息：

- 业务负责人 `business_owner`
- HR 负责人 `hr_owner`
- 审批时间 `approved_at`
- 大于 0 的整数样本量 `sample_size`
- 结果数据来源 `outcome_data_source`
- 审批说明 `approval_note`

任一治理项缺失时，不得把画像视为已确认基准。

## 3. 证据契约

每条证据必须包含可定位来源、原文摘录、方向和强度。证据强度定义如下：

| 强度 | 判定标准 | 可否支撑维度判断 |
|---|---|---|
| `strong` | 候选人描述了清晰、具体且可核验的情境、行动和结果，或给出多处一致的直接事实 | 可以 |
| `medium` | 有明确行为或经历，但情境、行动、结果中的部分信息不完整 | 可以 |
| `weak` | 只有概括性自述、标签、愿望或缺少行为细节的间接线索 | 可以，但不能单独支持中高置信度 |
| `missing` | 当前材料中没有可引用证据 | 不可以 |

证据方向只能用于两个位置：

- `evidence`：只接收 `supportive` 证据。
- `counter_evidence`：只接收 `counter` 证据。

不得把反证放入支持证据列表，也不得把支持证据放入反证列表。

## 4. 证据落地核验

模型给出的证据进入报告前必须逐条核验：

1. 来源必须真实存在：简历证据来源为“简历”，面试证据来源必须对应输入中真实存在的 `question_id`。
2. 摘录不得为空，经过空白字符规范化后必须是对应原始材料中的连续原文片段。
3. `missing` 不得作为有效证据。
4. 支持证据和反证的方向必须与所在列表一致。
5. 无法通过上述核验的条目必须删除，并记录证据问题，不得通过改写原文的方式伪造匹配。

报告中的有效证据按来源编号：

- 简历证据：`CV-E##`
- 面试证据：`INT-E##`

若没有有效反证，应明确写明“当前材料未发现有效反证；未发现不等于不存在”，不得把沉默解释为正面结论。

## 5. 水面上指标对齐

只允许评价成功画像中已经配置的水面上指标：

1. 模型遗漏的画像指标必须补齐为 `not_evidenced`。
2. 模型自行增加的指标必须删除并记录问题。
3. 指标状态使用标准枚举；模型输出的 `met`、`matched`、`partial` 等近义状态必须映射到系统标准状态。
4. 任一关键水面上事实缺失时，最终建议至少为“人工重点复核”，不得据此生成积极的确定性结论。

## 6. 维度证据阶段与覆盖度

四个维度分别独立判定，不得用一个维度的充分证据补偿另一个维度的证据不足。

每个维度的证据阶段为：

- `resume_hypothesis`：没有通过核验的面试支持证据，只能形成简历假设。
- `interview_supported`：至少有一条通过核验的面试支持证据。

覆盖度用于衡量当前有效材料对该维度的支撑完整性：

- 只有简历证据时，覆盖度上限为 55。
- 无有效支持证据时，覆盖度不能被模型给出的高数值用来抬升置信度。
- 证据问题按维度记录，并触发该维度降级，不得让单个维度的问题污染其他证据完整的维度。

## 7. 置信度确定性规则

置信度必须独立于候选人得分、画像目标分、综合分和相似度计算。高分不等于高置信度，低分也不等于低置信度。

按下列顺序判定每个维度：

1. 无有效支持证据：`low`。
2. 只有简历阶段：`low`，且覆盖度最多为 55。
3. 当前维度存在任一证据落地问题：`low`。
4. 存在 `strong` 反证：`low`，并禁止高置信度。
5. 同时满足以下全部条件时为 `high`：
   - 覆盖度不低于 80；
   - 至少两条有效面试支持证据；
   - 证据来自至少两个不同的 `question_id`；
   - 至少包含一条 `strong` 支持证据。
6. 同时满足以下全部条件时为 `medium`：
   - 覆盖度不低于 60；
   - 至少一条有效面试支持证据；
   - 至少包含一条 `medium` 或 `strong` 支持证据。
7. 其余情况均为 `low`。

覆盖度达到 80 但不满足高置信度的证据数量、来源分散度或强证据要求时，可以按中置信度条件判定为 `medium`，不得直接视为 `high`。

## 8. 得分、等级与画像对照

候选人维度得分、综合分和画像相似度只能表达基于当前材料的探索性结构化结果，不代表对人的能力、人格或未来绩效的确定性测量。

维度等级边界为：

- 80–100：优秀
- 60–79：中等
- 0–59：较差

但只有在画像为 `confirmed` 且该维度置信度为 `medium` 或 `high` 时才可展示等级。低置信度必须隐藏等级。

画像对照仅在同时满足下列条件时标记为可比较：

- 维度置信度不是 `low`；
- 该维度已有有效面试证据；
- 覆盖度不低于 60；
- 成功画像状态为 `confirmed`。

其余情况必须标记为不可比较。即使可比较，候选人分、画像目标分和差距也只能作为探索性人工复核线索，不得表述为确定性达标、胜任或录用结论。

## 9. 整体评估阶段

整体阶段由四个维度各自的证据阶段确定，不由模型自由选择：

- 四个维度都没有面试支持：简历预筛阶段。
- 部分维度有面试支持：部分面试支持阶段。
- 四个维度都有面试支持：完整面试支持阶段。

只要报告处于简历预筛阶段、成功画像为 `draft`，或存在证据问题，就必须展示探索性提示。

## 10. 建议语生成顺序

最终建议由代码按以下优先顺序生成：

1. 关键水面上事实缺失，或成功画像不是 `confirmed`：`人工重点复核`。
2. 存在证据落地问题：`建议补证`。
3. 任一维度置信度为 `low`，或任一维度覆盖度低于 55：`建议补证`。
4. 仅当综合分不低于 82、画像相似度不低于 78、整体覆盖度不低于 75，且不存在强反证时：`优先复核`。
5. 其他情况：`常规复核`。

所有建议都指向人工复核优先级，不得改写为自动招聘决定。

## 11. 追问闭环

追问必须是 HR 可以直接使用的完整问题，每项包含：

- `question`：完整追问句，不得只写 `Q1` 等编号。
- `purpose`：希望验证的假设或风险。
- `expected_evidence`：期望获得的情境、行动、结果和反思证据。
- `source_question_id`：关联的原面试问题编号；无直接关联时可为空。

若模型只返回问题编号，应尽量解析为原始面试题全文。结构不完整或无法解析时，使用成功画像中的首个相关行为锚点生成确定性兜底追问。

每个低置信度维度至少生成一条完整追问。优先级依次考虑：低置信度、低覆盖度、较大的画像差距和反证；最终优先追问最多保留 4 条。

## 12. 输出安全与审计

1. 对所有进入 HTML 的外部文本进行转义，禁止脚本或标签注入。
2. 模型生成字段中不得出现“建议录用”“建议淘汰”等自动决策措辞；发现后应阻断或中和。
3. 不得把探索性画像对照改写为确定性胜任、达标或绩效预测。
4. 报告必须声明正式结论由招聘方与业务负责人共同人工复核。
5. 审计信息至少包含报告编号、`schema_version`、`rules_version`、模型名称、画像版本与状态、生成时间和有效证据数量。
6. `dry-run` 只做输入和规则校验，不需要 API Key，也不得发起网络请求。
7. API Key 只从运行环境读取，绝不写入报告、日志、样例或项目文件。
